# 70 · 子代理编排可视化：任务树的完整方案

> 状态：**T100 已实施分道的第一层**（2026-09-29）。本文记录剩余层的取舍与实施顺序。
> 原则沿用 docs/50：先讲清代价，再决定做到哪一档，每批独立可回滚。

---

## 1. T100 交付了什么、还差什么

T100 打通的是「**进度可见**」：delegate 每步一条 `sub-step` WS 事件（persona 维度），
Web 端按角色分道渲染，delegate 收尾把「工具×次数」摘要追加进回显落库。

还差的三层：

| 层 | 现状 | 缺的东西 | 代价 |
|---|---|---|---|
| **L1 实时过程分道** | ✅ sub-step 事件 + 分道行 | — | 已付 |
| **L2 历史可回看** | 只有 `[子代理过程] bash×2` 摘要行 | 子代理的**逐工具步骤**（参数摘要/输出摘要）落库，点开 delegate 卡能看全程 | 中——StoredMessage.steps 是平的，要嵌套 |
| **L3 多层编排** | delegate 内还能 delegate（递归允许）但各层进度都挤在 `sub-step` 单一维度 | 事件带层路径（`parent/persona`），前端按树渲染 | 中高——事件模型要升级 |
| **L4 断点续跑编排** | 主回合有 checkpoint，子代理没有 | 子代理进度进 checkpoint，恢复时分道状态还原 | 高——checkpoint 格式升版本 |

## 2. 关键取舍

**L2 的落库形态是最大决策点。** 两个方向：

- **方向 A：嵌套 steps**（`msg.steps[i].sub = StoredMessage["steps"]`）。信息最全，但
  会话 JSON 体积可控性变差（子代理输出本来就大，T89 卸载后主层只留句柄——嵌套层也得照做），
  且 `steps` 的所有消费方（前端渲染/TUI 卡片/压缩 fitTranscript/checkpoint）都要升级。
- **方向 B：delegate 工具的 output 里带结构化文本**（现在的 `[子代理过程]` 的加强版：
  每工具一行「名称 · 参数摘要 · 输出前 80 字」）。零 schema 变更，所有消费方自动兼容
  （它就是字符串），压缩/卸载/落库全走既有链路。缺点：不可折叠交互、超长仍要卸载。

**先做 B。** 理由：L2 的用户价值八成来自「事后能看懂它干了什么」，八成场景 B 够用；
A 的全套改造（四消费方 + 卸载 + 压缩）是一个独立 Txx 的量级，等 B 不够用再上。
**判定信号**：如果用户开始要求「看子代理某一步的完整输出」，那就是 A 的时机。

**L3 的事件模型**：`sub-step` 加 `path: string[]`（如 `["coder","reviewer"]`），
前端 Map 的 key 从 persona 改为 `path.join(">")`。向后兼容：`path` 缺省 = `["persona"]`。
这个改动很小，可以随 L2 一起做；前端树形渲染是纯展示层，不急。

**L4 明确缓做**：子代理 checkpoint 恢复后「分道状态还原」的收益远小于主回合 checkpoint
（子代理通常几十秒到几分钟），先等真实长任务里出现「子代理跑了 20 分钟被杀」的案例。

## 3. 实施顺序

1. **B 批（L2，方向 B）**：delegate 收尾时把 onStep 累积的每步详情（工具名/参数摘要/输出截断）
   渲染成多行文本进 `[子代理过程]`；超长走既有卸载。验收：probe-delegate-progress 断言
   摘要含参数摘要；check-t100 加锚点。
2. **C 批（L3 事件升级）**：sub-step 加 `path`，前端 key 升级，递归 delegate 各层各一行。
   验收：probe-delegate-progress 加递归场景（子代理再派发）。
3. **A 批（L2 方向 A，仅当 B 被证明不够）**：嵌套 steps schema + 四消费方升级 + 卸载对齐。
   单独立项，不动手前先跑真实长任务采样确认需要。
